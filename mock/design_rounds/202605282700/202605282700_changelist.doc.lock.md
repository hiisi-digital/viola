## D1: v1.3.0 is a vocabulary extension, not a layout change

`NamVersion::V1_3_0` carries the same `NamPayload` / `NamFileEntry` / `NamNode` layout as v1.2.0. The only change is the `node_kind` id vocabulary growing with one identifier-leaf id. Because kinds are append-only and a `NamNode.kind` is an opaque `arvo::USize`, a v1.2.0 consumer still reads a v1.3.0 payload (it treats id 28 as an unknown number). The bump signals only that the producer MAY emit id 28. The `NamVersion` and `node_kind` DESIGN sections are updated to record the new version and the new kind.

## D2: which kind, and why this one

`IDENTIFIER` (id 28) names a plain identifier leaf: the name token of an item, function, field, variant, or binding. It is distinct from `TYPE_IDENTIFIER` (id 25), which names a type at a type position. A name-reading lint resolves the name by taking the node's source byte span.

The kind is chosen to unblock the cross-file item-name lints (the no-duplicate-fn cdylib port, mockspace #619): such a lint reads the name token of each function item to detect duplicate definitions. Without an `IDENTIFIER` kind a cdylib cannot tell a name-token leaf apart from any other unknown leaf.
