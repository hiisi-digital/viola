# What Slice 2 is for

Slice 1 shipped the static pipeline shape as six WU stubs plus a zero-sized
`ViolaConfigOpaque` placeholder. The placeholder exists because
`viola_config::ViolaConfig<'a, const MAX_PLUGINS: usize>` carries a borrow

The body reads `Resource<Workspace>` and `Resource<RunSurface>`, walks to

# Design question: the lifetime bridge

`viola_config::ViolaConfig` lives at `mock/crates/viola-config/src/lib.rs:69`:

```rust
pub struct ViolaConfig<'a, const MAX_PLUGINS: usize> {
    // borrowed slices into the parse buffer
    ...
}
```

The borrowed slices reference the TOML buffer the parser received. They cannot
outlive the buffer. `Resource<T>` in `hilavitkutin-api/src/store.rs:55` requires
`T: 'static`. Three resolutions are on the table.

## Option A: `ViolaConfigOwned`, copy into stable storage at parse time

Add a new owned type alongside `ViolaConfig`. Each borrowed `&'a str` is
interned via `hilavitkutin_str::Str` (already in viola's dep graph; produces a
stable `'static` handle). Each borrowed slice becomes a fixed-cap array via
`arvo::Cap<N>`-bounded storage.

The result type is
`ViolaConfigOwned<const MAX_PLUGINS: usize, const MAX_RULES: usize, ...>`. The
const generics scale with the toml's structure. `LoadConfig::execute` reads the
file into a stack buffer, parses with `ViolaConfig::parse`, then projects every
field through the interner into the owned form. The owned form is `'static` (no
borrow), so `Resource<ViolaConfigOwned<...>>` compiles.

Memory cost is bounded by the const-cap parameters. Parse-once invariant
preserved (every WU reads the same parsed result). No heap.

Drawback: const-generic explosion. The owned type has multiple cap parameters
(plugins, gates, severity rules, partial rules, plus their internal compounds).
Each cap must be threaded through the `Resource<T>` instantiation and every WU
that reads it. This is the `ViolaConfig<'a, N>` ergonomic issue compounded.

Mitigation: a
`pub type ViolaCfg = ViolaConfigOwned<MAX_PLUGINS, MAX_GATES, MAX_RULES, MAX_PARTIAL_RULES, ...>;`
alias at the `viola-config` crate root with workspace-default caps. Every
consumer references `ViolaCfg` instead of the full instantiation.

## Option B: re-parse on every WU read

Every WU that needs config calls `viola_config::parse(buffer)` inside its
execute body. The parsed result lives on the stack for that execute call only.
No `Resource<ViolaConfigOpaque>` write; the resource doesn't exist.

Simpler. Trivially compiles. No const-generic surface.

Drawback: wasted parse work, and a re-parse can be inconsistent if the file
changed between WU executes within one pipeline pass (it shouldn't, but the
invariant is now an implicit assumption rather than a typed one).

Bigger drawback: the AccessSet contract goes away. The dependency graph between
`LoadConfig` and `LoadPlugins`/`DiscoverFiles` is the entire point of declaring
`Resource<ViolaConfigOpaque>` in their access sets. Drop the resource and the
dependency analysis loses one of its real input signals.

This option is the wrong direction; it dissolves the work `Slice 1` did.

## Option C: feature-gate an owned variant in `viola-config`

Add `feature = "owned"` to `viola-config` that switches `pub struct ViolaConfig`
from borrowed to owned (via the same interner approach as Option A). Consumers
that need the borrowed form (the parser itself) get one variant; the
runtime/Resource consumers get the other.

Drawback: a single name in `viola-config` cannot have two structurally different
shapes through a feature flag without breaking type identity. The feature flag
flips would silently produce a different type with the same name, which is a
serde landmine.

Real shape: ship `ViolaConfigBorrowed<'a, N>` and `ViolaConfigOwned<...>` as two
distinct types, with `ViolaConfig` becoming a trait that both implement. This is
invasive to `viola-config`'s public surface and to the parser API. Multiple
consumer crates would need updating in lockstep.

Tractable but heavy for Slice 2. Maybe right long-term if the borrow/own split
matters at multiple call sites; today it only matters at the `Resource<>`
boundary.

## Recommendation

**Option A.** It is the canonical `hilavitkutin` Resource pattern: parse once at
the WU body site, intern through `hilavitkutin-str` (already in scope), bound
the variable-length lists with `arvo::Cap<N>`. The const-generic explosion is
mitigated by a single `pub type ViolaCfg` alias.

Option B dissolves the Slice 1 AccessSet work and is wrong. Option C is invasive
to a sibling crate and not needed until a second consumer wants the owned form.

The DOC CL stage (next phase) commits the option choice and the concrete
`ViolaCfg` cap parameters. The SRC CL stage lists the file edits.

# Field shapes for Workspace and CiState

Slice 1 ships `Workspace` and `CiState` as zero-sized markers. Slice 2 adds
fields per the original SRC CL's intent.

## Workspace

```rust
pub struct Workspace {
    pub path: hilavitkutin_str::Str,
    pub surface: viola_plugin_abi::RunSurface,
}
```

- `path`: the workspace root, interned. `Str` is already in viola's dep graph;
  suits a one-shot identifier like a workspace root.
- `surface`: a snapshot of the invocation context. Either matches the
  `Resource<RunSurface>` value or carries an independent classification.

Open question: do `Workspace.surface` and `Resource<RunSurface>` carry the same
value? If yes, the field is redundant; just read `Resource<RunSurface>`
directly. If different (Workspace records the invocation surface, RunSurface
routes diagnostics), the field stays.

The Slice 1 src CL hinted at the divergence ("an Lsp-initiated run egresses
through a Hook"). Carrying it as a `Workspace` field is fine; DOC CL captures
the call sites where the two diverge.

## CiState

```rust
pub struct CiState {
    pub is_ci: arvo::Bool,
    pub agent: AgentKind,
}

pub enum AgentKind {
    None,
    Human,
    Bot,
    Unknown,
}
```

- `is_ci`: `arvo::Bool` per the no-bare-primitives rule. True when CI env vars
  are set.
- `agent`: classifies who invoked viola. Detected from env (CI provider
  variables, user agent strings, presence of a TTY). DOC CL captures the
  detection logic and which env vars feed which variant.

# Body sketch for `LoadConfig::execute`

Illustrative pseudocode. The accessor method names below are placeholders; the
real Ctx surface comes from `hilavitkutin-api::context`
(`HasResourceProvider::resources()` plus the `*Api` trait methods). The `?`
operator does not apply to `WorkUnit::execute` (which returns `()`); the DOC CL
commits the real error path. Both fixed in the DOC CL phase, not here.

```rust
fn execute<'frame>(&self, ctx: &Self::Ctx<'frame>) {
    // Pseudocode. Real accessors per hilavitkutin-api::context.
    let workspace: &Workspace = ctx.read::<Resource<Workspace>>();
    let surface: &RunSurface = ctx.read::<Resource<RunSurface>>();

    // Read viola.toml into a fixed-cap stack buffer.
    let path = workspace.path.as_str();
    let mut buf = [0u8; CONFIG_MAX_BYTES];
    let bytes_read = read_file_into(path, &mut buf); // error path: DOC CL

    // Parse the borrowed form.
    let borrowed = viola_config::parse(&buf[..bytes_read]);

    // Project into the owned form (Option A).
    let owned = ViolaCfg::from_borrowed(&borrowed);

    // Write to the Resource.
    ctx.write::<Resource<ViolaCfg>>(owned);
}
```

Open questions for DOC CL:

- Concrete `CONFIG_MAX_BYTES` cap (depends on observed real viola.toml sizes;
  pick something generous).
- File-read primitive (`hilavitkutin-persistence` or a no_std platform-specific
  call).
- Error handling: `unimplemented!()` is the Slice 1 default; Slice 2's body
  needs real diagnostic emission. Likely through a `Resource<DiagnosticSink>`
  write that propagates to Slice 7's `EmitDiagnostics`. Both `read_file_into`
  and `viola_config::parse` are fallible, so the body cannot use the `?`
  operator inside a `()`-returning method; the failure path writes to the
  diagnostic sink and returns early.
- Interner state location for Option A. `hilavitkutin_str::Str` is a 4-byte
  handle backed by an interner that itself must live somewhere. The DOC CL
  locates the interner: a `Resource<StringInterner>` registered on the scheduler
  builder is the canonical answer; `LoadConfig` then reads or writes through
  that resource at parse time.
- The `Workspace.surface` versus `Resource<RunSurface>` divergence. The Slice 1
  src CL hinted at the case (Lsp-initiated run egresses through a Hook). DOC CL
  must close this before the SRC CL phase; either keep `Workspace.surface` as
  the invocation snapshot and let `Resource<RunSurface>` carry the routing
  target, or drop the redundant field.
