# Decisions committed

## Bridge: Option A with arena bundled in the owned form

`viola_config::ViolaConfig<'a, const MAX_PLUGINS: usize>` stays as the borrowed
parser output. A new owned form lands in the same crate:
`pub struct ViolaConfigOwned<...>` with const generics for every variable-length
list. Each borrowed `&'a str` in `ViolaConfig` becomes a `hilavitkutin_str::Str`
handle in `ViolaConfigOwned`. Each borrowed slice becomes a fixed-cap `[T; CAP]`
plus a `Cap<CAP>` length.

The arena that backs every `Str` handle in the owned form lives as a private
field on the owned struct itself:

```rust
pub struct ViolaConfigOwned<
    const MAX_PLUGINS: usize,
    const MAX_GATES: usize,
    const MAX_RULES: usize,
    const MAX_PARTIAL_RULES: usize,
    const ARENA_BYTES: usize,
> {
    pub plugins: [PluginEntry; MAX_PLUGINS],
    pub plugins_len: Cap<MAX_PLUGINS>,
    // gates, rules, partial_rules follow the same fixed-cap-plus-length pattern
    arena: ConfigArena<ARENA_BYTES>,
}
```

`ConfigArena<N>` is a small private newtype in `viola-config` over the
appropriate `hilavitkutin_str` interner arena (the concrete arena type lives at
the SRC CL phase; DOC commits the shape). The `Str` handles inside the owned
form reference offsets into `arena`; the bundle is `'static` (no borrows escape)
and slots into `Resource<T: 'static>` directly. No separate
`Resource<StringInterner>` is registered on the scheduler builder. The interner
is the parser's internal concern.

A type alias commits the workspace-default cap values:

```rust
pub type ViolaCfg = ViolaConfigOwned<
    MAX_PLUGINS, MAX_GATES, MAX_RULES, MAX_PARTIAL_RULES, ARENA_BYTES
>;
```

Consumers reference `ViolaCfg` not the full instantiation; the alias is the
contract.

The `viola-core::wus::ViolaConfigOpaque` placeholder Slice 1 introduced gets
deleted in this round. Per `.claude/rules/no-legacy-shims-pre-1.0.md`, no
deprecated alias remains. The `Resource<ViolaConfigOpaque>` claim in every WU's
Read or Write set becomes `Resource<ViolaCfg>` mechanically.

## Cap parameters

Five new caps land as `pub const` in `viola-config/src/lib.rs` alongside the
existing `SEVERITY_FILES_CAP`, `SEVERITY_COMPOUND_CAP`,
`SEVERITY_PARTIAL_FILES_CAP`:

| Cap                 | Value | Reasoning                                                                                                                                                                                      |
| ------------------- | ----- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `MAX_PLUGINS`       | 16    | Honours the existing `ViolaConfig<'a, N>` workspace-default. Pre-1.0; observed real configs use 2 to 4 plugins. Headroom for v2 plugin ecosystem growth.                                       |
| `MAX_GATES`         | 32    | One gate per lint. Pre-1.0 default; observed configs have under a dozen lints. Headroom of 2x past current usage.                                                                              |
| `MAX_RULES`         | 64    | Per-lint severity rules in `[[severity]]`. Pre-1.0 default; observed configs ship a handful of rules.                                                                                          |
| `MAX_PARTIAL_RULES` | 16    | Per-lint partial-match rules in `[[severity.partial]]`. Pre-1.0 default.                                                                                                                       |
| `ARENA_BYTES`       | 8192  | Backs every `Str` handle inside one `ViolaConfigOwned`. Plugin names plus paths times `MAX_PLUGINS` plus rule strings times `MAX_RULES` lands under 4KB in observed configs; 8KB doubles that. |

Each cap is a pre-1.0 workspace-default. The SRC CL phase cites at least one
real fixture config under `viola-cli/tests/fixtures/` when it commits these
values; if the fixtures show a larger envelope than the defaults, the caps move
at SRC CL time, not at re-locking time.

## Workspace.surface drops, only path stays

The TOPIC raised the redundancy: `Workspace.surface` and `Resource<RunSurface>`
carry overlapping data. The decision: drop `Workspace.surface`.
`Resource<RunSurface>` is the single source of truth for run-routing
classification. The host shim writes it; every WU that needs it reads it from
the dedicated Resource.

`Workspace` becomes:

```rust
pub struct Workspace {
    pub path: hilavitkutin_str::Str,
}
```

If a future case demands an invocation-surface snapshot that diverges from the
routing surface (the Slice 1 SRC CL hinted at "Lsp-initiated run egresses
through a Hook"), a separate `Resource<InvocationSurface>` lands when that case
materialises. Not in Slice 2.

The `Workspace.path` field is a `Str` handle into the same kind of arena that
backs `ViolaCfg`. Since `Workspace` does not carry its own arena, the host shim
is responsible for the arena that backs this `Str`. The simplest shape: the host
shim holds a long-lived `StringInterner` instance for its lifetime, the
`Resource<Workspace>` it populates contains `Str` handles into that interner,
and the interner outlives the scheduler run. This dependency is the host shim's
contract, not a Resource the scheduler manages.

## CiState fields and AgentKind

`CiState` gains the two fields the TOPIC named:

```rust
pub struct CiState {
    pub is_ci: arvo::Bool,
    pub agent: AgentKind,
}

#[derive(Copy, Clone, Debug, Default, PartialEq, Eq)]
pub enum AgentKind {
    #[default]
    Unknown,
    None,
    Human,
    Bot,
}
```

`Unknown` is `Default` because the host shim may set the value but the absence
of detection signal is the safer default. `None` is reserved for the case where
the host shim positively determined no agent is involved. `Human` and `Bot` are
the two positive identifications; the detection logic itself is the host shim's
concern, set at the resource write site in `viola-cli`.

## File-read primitive: viola-core does not open files

viola-core does not open files. The host shim (viola-cli) reads the workspace
`viola.toml` into a buffer and writes the buffer into a new
`Resource<ConfigBytes>`. `LoadConfig` reads from that Resource and parses.

`ConfigBytes` is a fixed-cap byte array with a length tracker.
`hilavitkutin_str::Str` is a 4-byte handle backed by an interner arena, not a
byte buffer; storing a 16KB TOML file content as a single `Str` would be a
category error. The right shape uses a raw byte array:

```rust
pub struct ConfigBytes {
    pub bytes: [u8; CONFIG_MAX_BYTES],
    pub len: Cap<CONFIG_MAX_BYTES>,
}
```

`CONFIG_MAX_BYTES` lands as `pub const CONFIG_MAX_BYTES: usize = 16384;` in
`viola-config/src/lib.rs`. 16KB caps the typical real viola.toml with
substantial headroom while staying stack-allocatable on every platform viola
targets. Real-world configs observed in the workspace are well under 4KB; the
cap quadruples that. The SRC CL phase cites an observed fixture range.

This decision aligns viola-core with the `hilavitkutin-workunit-mental-model.md`
rule: WorkUnit bodies do not perform runtime spawn or file I/O. The data plane
is the scheduler's Resource registry; the host shim populates it.

## Diagnostic flow: each WU writes its own `Column<Diagnostic>`

Slice 1 shipped `EmitDiagnostics` with `Read = Cons<Column<Diagnostic>, Empty>`
and `Write = Cons<Resource<DiagnosticSink>, Empty>`. The Column is the shared
scratch space where any WU that detects an issue appends a `Diagnostic`.
`EmitDiagnostics` reads the Column at pipeline end and pipes each diagnostic
through the sink Resource (stderr, JSON, LSP).

`LoadConfig` is the first producer. Its parse-error path writes a `Diagnostic`
into `Column<Diagnostic>` and returns early. `LoadConfig` does not declare Write
on `Resource<DiagnosticSink>`; the sink is `EmitDiagnostics`'s exclusive write
target, which keeps the contract clean (one Write declarer per Resource).

The body shape becomes:

```rust
fn execute<'frame>(&self, ctx: &Self::Ctx<'frame>) {
    // Pseudocode. Real accessors per hilavitkutin-api::context.
    let workspace: &Workspace = ctx.read::<Resource<Workspace>>();
    let bytes: &ConfigBytes = ctx.read::<Resource<ConfigBytes>>();

    let borrowed = match viola_config::parse(&bytes.bytes[..bytes.len.get()]) {
        Ok(b) => b,
        Err(e) => {
            ctx.push_to::<Column<Diagnostic>>(Diagnostic::from_parse_error(e));
            return;
        }
    };

    let owned = ViolaCfg::from_borrowed(&borrowed);
    ctx.write::<Resource<ViolaCfg>>(owned);
}
```

The accessor names here are still placeholder; the SRC CL phase commits the real
`hilavitkutin-api::context` surface.

## Updated LoadConfig AccessSet

Slice 1 shipped:

```rust
type Read = Cons<Resource<Workspace>, Cons<Resource<RunSurface>, Empty>>;
type Write = Cons<Resource<ViolaConfigOpaque>, Empty>;
```

Slice 2 updates to:

```rust
type Read = Cons<Resource<Workspace>,
             Cons<Resource<RunSurface>,
             Cons<Resource<ConfigBytes>, Empty>>>;
type Write = Cons<Resource<ViolaCfg>,
              Cons<Column<Diagnostic>, Empty>>;
```

Three Reads (Workspace, RunSurface, ConfigBytes) and two Writes (ViolaCfg as the
parsed output, Column<Diagnostic> for the error path). No interner Resource
appears; the arena that backs `Str` handles inside `ViolaCfg` is a private field
of `ViolaConfigOwned`. The arena that backs `Workspace.path`'s `Str` handle is
the host shim's long-lived interner, contracted into existence at
scheduler-builder time but not exposed as a scheduler Resource.

## `LoadPlugins` and `DiscoverFiles` updates

`LoadPlugins` was `Read = Cons<Resource<ViolaConfigOpaque>, Empty>` and
`Write = Cons<Column<PluginEntry>, Empty>`. Slice 2 updates the Read to
`Resource<ViolaCfg>`. `PluginEntry`'s field shape is Slice 3 scope; this CL does
not commit it, except to note that any name field uses a fixed-cap byte array
rather than a `Str` (avoids cross-WU arena coupling).

`DiscoverFiles` was
`Read = Cons<Resource<Workspace>, Cons<Resource<ViolaConfigOpaque>, Empty>>` and
`Write = Cons<Column<FileInfo>, Empty>`. Slice 2 updates the Read swap from
`ViolaConfigOpaque` to `ViolaCfg`. `FileInfo`'s field shape is Slice 4 scope.
