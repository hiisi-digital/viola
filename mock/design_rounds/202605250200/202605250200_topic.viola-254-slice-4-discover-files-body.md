# Design tensions and the chosen path

## Filesystem walking: host shim, not WU

The hard tension: viola is `#![no_std]` with no alloc per the workspace rule, and the `forbidden-imports/viola*` lint blocks `std::*` and `alloc::*` in every viola crate. Filesystem walking inherently uses syscalls. The walker has to live somewhere. Three paths considered:

- **Path A: in-WU walker via libc-syscalls.** Mirror the `hilavitkutin_linking::Library::load` pattern (which calls dlopen via a stack crate that wraps libc). Write a `hilavitkutin-fs` or similar stack-side helper. The walker lives in the stack; the WU body calls it.
- **Path B: host shim walks, WU projects.** The host shim (viola-cli) walks the filesystem at scheduler-builder time, interns each discovered path through the host's long-lived interner, and writes the result into a new `Resource<DiscoveredFilePaths>`. The WU body reads that Resource and projects each entry into a `Column<FileInfo>`. No filesystem syscalls inside the WU; viola-core stays pure no_std data-transformation code.
- **Path C: defer everything.** Wastes the slice.

This round picks **Path B**. Rationale:

1. The hilavitkutin-workunit-mental-model.md rule says host shims populate Resources at scheduler-builder time; WUs project that data into Columns. The LoadConfig Slice 2b body matches this: the host shim populates `Resource<ConfigBytes>`, the WU parses it into `Resource<ViolaCfg>`.
2. The hilavitkutin-fs stack-side walker (Path A) is its own design conversation: error semantics for partial reads, symlink loop detection, max-depth caps. None of those questions are answerable inside Slice 4 scope.
3. Path B keeps viola-core's `no_std` claim honest without threading a `lint:allow` for an unverified-yet stack crate.

Path A stays an open question. BACKLOG entry tracks it.

## Include / exclude pattern matching: not in this round

The scoping memo says DiscoverFiles "honour the config's include / exclude patterns." `viola_config::ViolaConfigOwned` today carries `plugins`, `gates`, `rules`, and `partial_rules` but no `includes` or `excludes` field. This round defers include / exclude pattern matching entirely. BACKLOG entry captures the deferral; the future slice that lands include / exclude in viola-config also extends `DiscoverFiles` Read to include `Resource<ViolaCfg>` and adds the matcher to the body.

## AccessSet: match body usage exactly

Slice 1 declared `Read = Cons<Resource<Workspace>, Cons<Resource<ViolaCfg>, Empty>>` and `Write = Cons<Column<FileInfo>, Empty>`. The Slice 1 declaration was forward-looking; the Slice 4 body actually consumes only `Resource<DiscoveredFilePaths>` and writes only `Column<FileInfo>`. AccessSet declarations are scheduler-visible contracts that force serialisation around named Resources. Declaring access that the body does not consume costs scheduler concurrency for no benefit.

This round narrows the AccessSet to match body usage exactly: Read becomes `Cons<Resource<DiscoveredFilePaths>, Empty>`; Write stays `Cons<Column<FileInfo>, Empty>`. Future slices that consume Workspace, ViolaCfg, or write `Column<WuDiagnostic>` extend the AccessSet at the point of consumption. The BACKLOG entries for filtering, kind classification, and Workspace-relative diagnostic context all anticipate their own AccessSet extensions.

## `FileInfo` ZST flip

Slice 1 declared `FileInfo` as `pub struct FileInfo;` (ZST). The body needs the path at minimum; future lint plugin invocations may also need file-kind classification. Slice 4 ships the minimal two-field shape: `path: hilavitkutin_str::Str` and `kind: FileKind` (enum: Regular, Symlink, Other). Size hints defer to a follow-up.

## `DiscoveredFilePaths::push`: unsafe with Safety clause

The Resource's `push` API is the host-shim-only seam. Its soundness rests on a temporal contract (called between `Scheduler::builder()` and `Scheduler::build()` only) plus the four-invariant Sync contract (sole-producer at builder time, single-threaded build phase). A safe public function whose soundness depends on a documented runtime contract is a footgun; any consumer crate can call it at any time and silently break the invariant.

Slice 4 marks `push` as `pub unsafe fn push(...)` with a `# Safety` clause naming the four invariants the caller must uphold, mirroring `ExtensionHost::push`'s pattern. The host shim in viola-cli calls it inside an `unsafe { ... }` block at scheduler-builder time.

# What lands in source

In `viola-core/src/resources.rs`: new `DiscoveredFilePaths` Resource. Fixed-cap array of `hilavitkutin_str::Str` handles plus a `Cell<arvo::Cap>` length counter. `MAX_DISCOVERED_FILES: usize = 4096` const cap. `unsafe impl Sync` carries a four-invariant SAFETY note. `push` is `pub unsafe fn` with a `# Safety` clause; `paths_len` and `path_at` are safe read-only accessors.

In `viola-core/src/wus/mod.rs`: `FileInfo` ZST flips to `{ path: Str, kind: FileKind }`. `FileKind` enum lands as a closed-vocabulary three-variant enum (Regular, Symlink, Other) per the closed-enum-as-spec discipline.

In `viola-core/src/wus/discover_files.rs`: AccessSet narrows to match body usage. Body reads `DiscoveredFilePaths` Resource, iterates `paths_len()` slots, projects each `Str` handle into a `FileInfo { path, kind: FileKind::Regular }`, writes to `Column<FileInfo>` via local-counter slot. The `Maybe::Isnt` arm from `path_at` is unreachable by the loop-bound contract; the body uses `unreachable!()` to assert that and surface a logic bug if it ever fires.

In `viola-core/tests/discover_files.rs`: compile-time AccessSet-shape witness via sealed `IsSame<X>`, paralleling the Slice 3 `tests/load_plugins.rs` test.
