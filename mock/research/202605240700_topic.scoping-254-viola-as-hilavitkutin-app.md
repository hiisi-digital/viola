## Purpose

This is a scoping memo, not a design round. The design is already locked in `docs/internal/HILAVITKUTIN-APP-SHAPE.md`. This memo enumerates the concrete implementation slices, their dependencies, the existing source that gets restructured or dissolved, and a recommended slice ordering. The intent is to put a human (op) in a position to pick up #254 implementation with a clear map, without first having to re-derive what needs to happen.

## What's already settled (do NOT re-design)

Both #254 design questions closed 2026-05-24 via three-parallel-specialists convergence. Captured in the cdylib boundary memo's "Deferred but load-bearing" section. The implementation does not get to revisit these:

- **Cdylib FFI shape**: `LintEvaluateVtable.evaluate(host_ctx, nam, config_bytes, config_len, out_batch) -> AbiStatus` (direct args, no wrapper struct). Already shipped in `viola-plugin-abi`.
- **Meta-virtual registration**: `WorkUnit<Schedule = Always>` generic parameter on the `WorkUnit` trait. Lifecycle WUs implement `WorkUnit<On<Marker>>`. Standard `.with(WuStruct::default())` registration. Landed precedent: `impl WorkUnit<On<ScheduleEnd>> for AdaptWu` at `hilavitkutin-providers/src/adapt_wu.rs:63`.

The store table and WorkUnit table in `HILAVITKUTIN-APP-SHAPE.md` are the canonical source of truth. The phase shape there is what the scheduler derives from the AccessSets.

## What changes in viola-core

The current `viola-core` is a hand-rolled host runtime: `RunScope` struct, `CaptureSink` struct, `Session<N>` for plugin LIFO, `pipeline::run` function, hand-rolled sequential dispatch loop. None of these survive the restructure.

What replaces them, per the HILAVITKUTIN-APP-SHAPE.md:

| Old shape | New shape | Location |
|---|---|---|
| `pipeline::run` | `scheduler.run()` driven by registered WUs | viola-cli main |
| `RunScope` (struct) | Set of Resources: `Workspace`, `CiState`, `RunSurface`, `ViolaConfig` | viola-core/src/resources.rs (new) |
| `CaptureSink` | `Column<Diagnostic>` | scheduler-managed |
| `Session<N>` | `Resource<ExtensionHost>` (re-exported hilavitkutin-extensions type) | scheduler-managed |
| Hand-rolled dispatch | `Scheduler::run()` over `WorkUnit` graph | scheduler-managed |
| `RunScope` as FFI wire shape | Survives ONLY as `#[repr(C)]` runner-vtable arg | viola-plugin-abi (unchanged) |

## New WorkUnit declarations (the implementation surface)

Per HILAVITKUTIN-APP-SHAPE.md's WorkUnit table. Each row below maps to one new `impl WorkUnit` block in viola-core. The implementation slices are roughly one WU per slice (or small clusters where dependencies are tight).

| WorkUnit | Schedule | Slice priority | Notes |
|---|---|---|---|
| `LoadConfig` | `Always` | First | Reads `Resource<Args>`, `Resource<Env>`. Writes `Workspace`, `CiState`, `RunSurface`, `ViolaConfig`. Depends on viola-config parser (already exists). |
| `LoadPlugins` | `Always` (could also work as `On<PlanStage>` per spec; settle during impl) | Second | Reads `ViolaConfig`. Writes `Resource<ExtensionHost>`. Replaces `Session<N>::push` LIFO. |
| `DiscoverFiles` | `Always` | Third | Reads `Workspace`, `ViolaConfig`. Writes `Column<FileInfo>`. New surface; not in current source. |
| `RunRunner` | `Always` | Fourth | Reads `ExtensionHost`, scope resources, `Column<FileInfo>`. Writes `Column<Nam>`. Replaces the runner-invoke portion of `pipeline::run`. |
| `RunLint<const L: usize>` | `Always`, `COMMUTATIVE = Bool::TRUE` | Fifth | Reads `ExtensionHost`, `Column<Nam>`. Writes `Column<Diagnostic>`. `MAX_LINTS` const slots. Cdylib dispatch per the boundary memo. |
| `EmitDiagnostics` | `Always` or `On<ScheduleEnd>` (settle during impl based on whether emit is per-pass or per-run) | Sixth | Reads `Column<Diagnostic>`, `ViolaConfig`. Writes via writer-provider (stderr / JSON). Replaces `CaptureSink::report`. |
| `AdaptWu` | `On<ScheduleEnd>` | Already exists | From `hilavitkutin-providers`. Just `.with(AdaptWu::default())` in the builder. |

`COMMUTATIVE = Bool::TRUE` on `RunLint<L>` is the load-bearing claim for parallel fan-out per the cdylib memo's first remaining deferral (cross-WU commutative writes verification against landed dispatch codegen).

## Recommended slice plan

One PR per WorkUnit (or small cluster) keeps review tractable. Each slice can land independently and be tested in isolation by registering only the WUs that exist at that slice.

- **Slice 1: scaffolding** — Create `viola-core/src/resources.rs` defining `Workspace`, `CiState`, `RunSurface`, `ViolaConfig` as `Resource<T>`-shaped types. Create `viola-core/src/wus/` module tree (one file per WU, all empty stubs that implement `WorkUnit` with deferred bodies). Compiles green; nothing functional yet.

- **Slice 2: `LoadConfig`** — Implement the body. Pull from existing `viola-config` parser. Tests: scheduler-built fixture with `LoadConfig` + verify Resources populated.

- **Slice 3: `LoadPlugins`** — Implement. Test against the existing `viola-test-plugin-fixture`. Replaces the `Session::push` callsites; delete `Session<N>`.

- **Slice 4: `DiscoverFiles`** — Implement. New surface; tests verify file walking.

- **Slice 5: `RunRunner`** — Implement. Marshals `RunScope` `#[repr(C)]` from Resources at the FFI call site. Tests against `viola-test-runner-fixture`.

- **Slice 6: `RunLint<L>`** — Implement. The big one. `const L: usize` slot pattern. Cdylib dispatch per cdylib boundary memo Shape D. Tests: multi-lint fan-out via `viola-test-plugin-fixture`.

- **Slice 7: `EmitDiagnostics`** — Implement. Replaces `CaptureSink`. Tests: human-readable + JSON output.

- **Slice 8: `viola-cli` rewires to `scheduler.run()`** — Delete `pipeline::run`. Wire `main` to build a scheduler with all WUs registered, call `run()`. Delete `RunScope` struct from `viola-core` (only the FFI version in `viola-plugin-abi` survives). Delete `CaptureSink`, `Session<N>`.

- **Slice 9: parallel fan-out verification** — Audit pass against the landed hilavitkutin dispatch codegen to confirm the COMMUTATIVE flag yields actual reduce-style parallel fan-out across `RunLint<0>..RunLint<MAX_LINTS-1>`. If it serialises, the design needs revisiting per the cdylib memo's first remaining deferral.

## Dependencies between slices

- Slice 1 must land first (defines the Resource types every other WU reads/writes).
- Slices 2 through 7 are independently developable once Slice 1 lands; their declared AccessSets enforce the dependency graph at compile time.
- Slice 8 needs all previous slices.
- Slice 9 is the validation pass after Slice 6 + 8.

## Things to settle DURING implementation

These are small calls the spec leaves implicit; pick during the corresponding slice and document in that PR:

- `MAX_LINTS` value (viola-cli configuration; sane default 32 or 64).
- Whether `LoadPlugins` is `Always` (runs at each scheduler pass) or `On<PlanStage>` (runs once at build). Argues for `On<PlanStage>` because plugins load once per process lifetime.
- Whether `EmitDiagnostics` is `Always` (per pass) or `On<ScheduleEnd>` (per run). Argues for `On<ScheduleEnd>` because viola is a one-shot tool, not a continuous loop.
- The `Args` and `Env` Resource types: probably `arvo::USize`-and-`Str`-shaped read-only carriers. Their exact shape lives in viola-cli's main where args parse via clap.
